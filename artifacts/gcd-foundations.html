Euclid, typed by what it returns

A type is a set. The type of a program fragment is a pair of sets, the states it starts from and the states it ends in; the type of a function is the set of values it may return. In the calculus on this page the five typing rules each have one picture, a proof is those pictures plugged together, and the output of Euclid's algorithm is typed {r | Div(r) = CD(a, b)}: a number whose divisors are exactly the common divisors of the inputs. Every picture below is computed from the a and b in the bar above; change them and the sets move.

The page shows the type before the run. The derivation (filled cells) is the proof: it covers every state in a set at once. The run (dark-blue rings, from the run slider) is evidence: it visits a handful of those states. Dark red means a premise is false, and nothing else.

2 · the calculus

Five rules, five pictures

States are tuples of small natural numbers (here every variable ranges over 0..32); a type {s | P} is the set of states where the formula P holds, and a judgment c : A ⇒ B says: started in any state of A, the fragment c runs without trapping and ends in a state of B. Formulas are comparisons, divisor-set equations and conjunctions over the expression language; there is no quantifier the reader has to instantiate, because a divisor set Div(e) is itself a value the evaluator can compute.

expressions   e ::= n | x | e mod e
divisor sets   S ::= Div(e) | CD(e, e) (= Div ∩ Div)
formulas   P ::= true | e = e | e ≠ e | e < e | e ≤ e | S = S | S ⊆ S | P ∧ P
types   A, B, I ::= {s | P}   results   {r | P}
fragments   c ::= x̄ := ē | c ; c | while P inv I measure e do c
functions   fun f(ā) : {r | P} = c ; return e

Each rule is drawn with the same grammar: a type is a panel of filled cells; a rule application is a dock (pale ribbon) carrying the rule's name and the program text; containment is one set drawn over another. Dotted eval marks a fact the trusted evaluator computed by enumerating the domain; everything else is derived by the rule. The pictures here use a small 0..8 domain so the cells are large.

Composition

Two derivations plug together when the output panel of one is the input panel of the next: the same set, so the same picture. That is the whole content of SEQ, and it is what every larger picture on this page is made of. Where the sets are not the same, SUB inserts the overlay panel; if the overlay shows a dark-red cell, the pieces do not fit.

3 · the program

Euclid, and the type of its answer

The result type is {r | Div(r) = CD(a, b)}: the divisors of r are exactly the common divisors of a and b. This is the simplest honest characterization. It is first-order and finite (for inputs up to 32, every divisor set is a 32-bit mask the evaluator computes directly); it needs no greatest, so it has nothing to say about ordering and it is right at gcd(0, 0) = 0, where "greatest" fails; and it has exactly one inhabitant for every a, b, so the type pins the answer down. Above all it makes the loop invariant a picture of a set that does not move: Euclid's step replaces (x, y) by (y, x mod y) and keeps the set of common divisors fixed. (The recursive characterization r = gcd(a, b) with gcd defined by Euclid's own equations would be circular as a specification: it says the program computes what the program computes.)

Here is the program in the calculus, each line annotated with the type it leaves behind. The invariant I and the measure y are the only two things a programmer must write that are not code.

5 · the checker


What is checked, and what is refused


The checker in this page is about 120 lines. It walks the derivation tree and, at every node, computes the two sets a rule talks about and compares them cell by cell: ASSIGN builds the exact image of the input set and refuses if the expression is undefined on any state (x mod 0); SEQ requires the output set of the first part to equal the declared input set of the second; SUB requires the set we have to lie inside the set we claim; WHILE requires the body to start from I ∧ guard, end inside I, and move every row k of the measure strictly below k; FUN requires the body to start from every state and end in the result type read through return e. Four mistakes are seeded. Each is refused at exactly the dock whose premise is false, drawn below for the current a, b.









6 · what is trusted, and what the calculus cannot do


The trusted base, plainly


    
  
  • The evaluator. The meaning of mod (undefined when the divisor is 0), of comparison, of Div as a bitmask over d = 1..32 (Div(0) is every d), and of simultaneous assignment. These are 25 lines of JavaScript. If they are wrong, every proof is wrong.
    • 
  
  • Enumeration as the decision procedure. Every leaf premise (containment, equality of sets, definedness, measure decrease) is decided by evaluating the formula on all 1089 states of the 0..32 grid, for the chosen a, b; the all slices button repeats this for all 1089 pairs (a, b). For this bounded domain the result is a proof, and for this bounded domain exhaustive testing of the program would also have been a proof. The derivation earns its keep elsewhere: it says why (the invariant), in a form whose size does not grow with the domain, and the identical tree is the proof for 32-bit integers once the three leaf facts (CD(y, x mod y) = CD(x, y), x mod y < y for y ≠ 0, CD(x, 0) = Div(x)) are discharged by lemma or by an SMT solver instead of by enumeration. Hover the three docks that use them.
    • 
  
  • The checker itself (the five rule cases, ~120 lines), and the fact that the pictures are drawn from the checker's own sets rather than from a separate renderer.
    • 



What it cannot do


    
  
  • No unbounded domains and no 32-bit arithmetic: the calculus is sound for the domain it enumerates. Nothing here proves anything about gcd(1071, 462).
    • 
  
  • No conditionals, no nested loops, no function calls, no memory. if would be a sixth picture (split a panel by the test, two pictures, union); nested loops would need the measure premise to be checked compositionally rather than by running the loop-free body on each row.
    • 
  
  • Types mention only program variables and the immutable parameters; there are no logical variables, no quantifiers, no ghost state. The divisor-set language is the one piece of "theory" built in, and it is built in as a computable value, not as an axiom.
    • 
  
  • Invariants are written by hand. The checker checks; it does not search. A missing or weak invariant is refused, not repaired.
    • 
  
  • The run is evidence only. A ring inside a filled cell adds nothing to the proof; a ring in an empty cell would mean the trusted base is wrong.
    • 



In Codillon's terms: every panel would sit in the margin of one line; the dock is the pale ribbon that already joins a producer to a consumer; the loop bracket would carry the invariant panel and the measure triangle; and the step slider would move the ring.
