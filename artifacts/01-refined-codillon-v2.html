Refined Codillon, version 2: proofs you can see

Codillon is Keith Winstein’s structured editor for WebAssembly, written for Stanford’s CS 10N. You type one instruction per line. On every keystroke Codillon re-validates and re-runs your module and draws what it knows in the margin: each value’s type is a shape, the operand stack is a set of curves from producer to consumer, anything wrong is darkred, and a slider moves you through the run. Refined Codillon adds one idea: a type is a set of values, and the proof that a value lies in the smaller set is itself a value, drawn with the same cups and curves as everything else.

This is the second version of the design. Version 1, the first iteration, wrote specs in a separate annotation language ((@requires …), (@invariant …)) and sent them to Z3. Version 2 drops both. A comparison followed by if or br_if gives each branch a fact. Facts travel in a fact lane beside the code. Every proposition an instruction needs is a proof cup, and a proof cup is fed by exactly one fact, along a wire you can see. Arithmetic steps are written as prove k lines and checked by a small deterministic kernel. It never answers “unknown”, and it has no Z3 or SMT solver underneath. Why the design changed, and what the change costs, is in research 18. The design itself is research 16, and the conversation that started it is research 15.

Every big picture on this page is the real editor: the Codillon fork on branch proofs, compiled to WebAssembly, running the same examples you can open yourself. Drag its slider, scroll inside it, or use “open in editor ↗” to edit the same state in a new tab. A few small drawings are labelled diagram. They show ideas the editor does not draw on its own.

1 · A type is a set

An i32 has 2³² possible values. A refinement (i32 | P) keeps only the values where P holds. In version 2, P is not a formula in a separate logic. It is a WebAssembly function: a pure, total, loop-free function that returns an i32, read as true when it is nonzero. $is_even is four ordinary instructions: local.get $x, i32.const 1, i32.and, i32.eqz. So (i32 | $is_even) is the set of values on which that code returns nonzero, and the same code runs when you test it.

A spec is written in the places Wasm already has types:

  • Function types are contracts. A refined parameter is a precondition that every caller must prove. A refined result is a postcondition that the body must prove.
  • Block types are invariants. loop $grow (fact (call $sq_le …)) says that fact holds every time control reaches the loop head, so every back-edge must supply it. There is no @invariant.
  • A functional spec is a harness. A harness is an ordinary exported function that calls the code, computes a check, and skips an unreachable when the check passes. unreachable has one cup, and that cup needs a proof of False. Proving False there means no input reaches it, which means the spec holds for all inputs. Running the same harness on one input is an ordinary test.

Four verdicts, one cup

After checking, every cup is in exactly one of four states. A fifth mark, proven*, flags a proof that rests on something only checked at run time. The states differ in fill pattern as well as color, so they survive grayscale printing. Darkred means a real violation and nothing else, and there is no green.

Gradual and strict. The editor runs in gradual mode by default. A cup with nothing feeding it does not stop you. The editor compiles it into a check that runs before the instruction, so the program still runs and still tells the truth on every input you give it. The header gets a gray 1 runtime check badge. In strict mode (&strict=1, or the strict switch) the same cup is an error, “nothing feeds it”. A function earns VERIFIED only when it is strict-clean. Gradual mode shows the badge too, so you can see which functions are already proven while everything still runs.

Why there is no “unknown”. The kernel never asks whether a proposition is true. It asks whether the text contains a derivation of it, and it decides that by lookup, bounded evaluation and one decision procedure with fixed caps. When there is no derivation, the cup is unfed. That is a fact about the text, and you fix it by adding a line. A prove that fails is a failed line with a countermodel or a named cap. Version 1 could show an indigo “?” when Z3 timed out, and the same text could be proven on one machine and undecided on another. Version 2 cannot.

2 · Reading a line

Every instruction already has a fraction just left of its text, with its inputs as cups above a rule and its outputs as shapes below it. Version 2 keeps that layout and adds four things.

  • Proof cups are diamonds in the same fraction, to the right of the value cups. A division has a diamond for b ≠ 0. A load or store has one for its bounds. A call to $half has one for $is_even($x). A loop’s back-edge has one for each invariant, and unreachable has one for False.
  • Facts are born at fixed points: an if or br_if arm, a block’s end, a call’s result, function entry, a prove line or a lemma line. A fact stays in the lane until its block arm ends, like a path condition. Facts are never popped, so ordinary lines keep their stack effect.
  • Wires. Every fed cup has a thin purple wire from the fact that feeds it. The wire is always drawn, not only on hover. A cup is fed in exactly one of two ways. Either a prove line directly above feeds it, or the kernel finds the identical fact in the lane (an exact match, not a search).
  • Fraying. When local.set $x rebinds a variable that a fact is about, that fact’s ribbon frays. It is still a true fact about the old value, so it cannot feed a cup about the new one.

prove k

Some cups need a step of arithmetic, not a lookup. prove k takes the k most recent facts in the lane as hypotheses, drawn as k diamond cups on its own fraction with wires back to where those facts were born. It proves the goal of the cup it feeds: the first unfed cup on the next ordinary line. The decision procedure (research 16 §3) is linear integer arithmetic over unsigned readings. It handles wraparound with explicit wrap variables, treats a monomial like r·r as an atom, and has fixed caps of 64 terms, 24 variables, 32 atoms and 256 cases. Nonlinear facts beyond monomials have to be lemmas. When a prove fails, its commentary names the hypotheses it actually took, which is how you catch the wrong k.

Here is the isqrt loop in the real editor. The loop’s block type on line 34 is the invariant $sq_le(r, n). Line 38, prove 2, takes the two most recent lane facts, the invariant and the local’s refinement u($r) ≤ 65535. Because it feeds the taken edge of the br_if below it, it also gets that branch’s own condition, u($r) ≥ 65535. Together these pin r = 65535, and the step proves the exit fact $is_isqrt(r, n) that block $done (line 32) requires of every branch to it. Line 57 (prove 2) proves that r + 1 still fits the refined local, using the guard’s fall-through u($r) < 65535. Line 59 (prove 3) proves that the back-edge supplies the invariant.

3 · Lesson 1 · parity

$half takes only even numbers: (param $x (i32 | $is_even)) is a precondition that every caller must prove. $half_or_neg1 earns that fact with a gate. Line 43 negates $is_even($x), so the if on line 44 sends odd numbers to the then-arm. The else-arm starts with the fact ¬¬$is_even($x), which R4 normalizes to $is_even($x), and the call to $half on line 49 finds it in the lane by exact match. No prove is needed. Each arm then proves the function’s result type $hon_ok with one prove line. The harness $parity_ok ends in unreachable, and its False cup is proven from the call’s result fact and the failed check.

4 · Lesson 2 · integer square root

$isqrt counts r up while (r+1)² ≤ n. The spec has two parts, and neither is an annotation. The result type says $is_isqrt(r, n). That is an ordinary i64 Wasm function computing r² ≤ n < (r+1)², in i64 so that the check itself cannot overflow. The harness calls $isqrt, runs the same predicate, and skips unreachable when the check passes.

  1. The loop invariant is the loop’s type. loop $grow (fact (call $sq_le …)) on line 34 holds on entry (line 33, prove 0, from r = 0), and the back-edge must supply it again (line 59).
  2. A refined local is a second invariant. (local $r (i32 | (i32.le_u v 65535))) keeps every square linear in a monomial atom and inside i64. The cost is the early exit at 65535.
  3. unreachable consumes False. The harness’s prove 2 on line 73 takes the call’s result fact and the fall-through fact “the check failed”. Together they contradict each other, so the step derives False and the ⊥ cup on line 74 is proven. That proof is the theorem: for every n, $isqrt(n) is the integer square root.

5 · Lesson 3 · a hash table

The table has 8 i32 slots in the last 32 bytes of memory (addresses 65504–65535), with 0 for empty, −1 for a tombstone, and linear probing. Every load and store has a bounds cup, and all of them are proven. Masking the index with and 7, a guard, or $find’s result type supplies the fact. The representation invariant $rep_ok is a recursive Wasm predicate over memory, with a measure. It says no key appears twice and every probe chain is unbroken. It is threaded through $insert and $remove as a fact parameter and a fact result.

Here v2 is honest about a gap. Version 2 has no memory frame rules. Nothing says “this store does not touch slot j”. After a store, every fact about a memory-reading predicate is gone, because the memory epoch has changed. So the invariant cannot be carried across a store. Of the table’s 29 cups, 7 are runtime-checked for exactly this reason: 2 in $insert, 1 in $remove and 4 in the harness. The headers say so with gray badges. The other 22 are proven, 3 of them only relative to those checks (proven*). The alternative is an instructor axiom per store, and the example declines it. Frame rules are open question 2 in research 16 §9.

6 · Lesson 4 · vericoding

In vericoding mode the student writes the spec and someone else writes the implementation and its proofs. That someone can be the student, an LLM, or a recorded session. The kernel is the only judge. The LLM is never trusted, and the editor works fully without one.

The ownership boundary

locked: the student ownsopen: the implementation side owns
every function header (types, refinements, fact parameters and results, exports), except lemma headersbodies of ordinary functions
bodies of predicates, measures and harnesseslemma functions, header and body
axioms (axiom: exports) and assume linesproof lines: prove, lemma, unfold, fact locals
block-type facts marked ;; @own, memory and global declarationsblock-type facts and refined locals it adds

After every round the kernel checks four things. Locked lines are unchanged, compared by a hash taken when the session starts. The open side added no assume, no axiom, no import, and no call to a function that is neither in the module nor one of its own lemmas. Every cup in the code it touched is proven, with no runtime checks and no proven*. Every harness ⊥ cup is proven. A submission is accepted only if every function it touched is strict-clean, and therefore VERIFIED. The editor itself stays in gradual mode, so a rejected submission still runs.

Adequacy: is the spec worth proving?

A proof only says the code meets the spec. The adequacy panel checks the spec itself, without any LLM. It has two parts.

  • Vacuity. The kernel tries to prove False from a function’s parameter refinements alone. If it succeeds, every claim about that function holds trivially. Separately, the runner looks for at least one test input that satisfies the precondition. gcd-vacuous meant to write a ≥ 0 as (i32.gt_s v -1) but wrote gt_u, which means u(a) > 2³²−1. No input satisfies that. The harness is then “proven” without even the axiom, and the kernel alone cannot tell. The panel flags it as VACUOUS: 0 of 64 inputs satisfy the precondition.
  • Mutation. The runner mutates the implementation one site at a time with six operators: relational flip, signedness swap, constant off by one, arithmetic swap, operand swap and condition inversion. It then runs every harness. A mutant that survives is either equivalent to the original or a sign that the spec is too weak. For the verified $isqrt, 8 of 24 mutants survive, and 6 of those the kernel still proves. Examples are i32.const 65535 → 65536 and ge_u → gt_u on the guard. These are equivalent mutants. The guard is a safety stop, and whenever it fires the (r+1)² > n test would exit at the same r. The values involved (r ≤ 65535, and squares far below 2⁶³) are small enough that signed and unsigned readings agree. The panel lists them and leaves the judgment to the student.

The live LLM is optional

The recorded sessions need no network and no key, so a classroom demo works offline. To try a live session, paste your own OpenRouter key into the panel’s “LLM” section. The key stays in your browser’s localStorage and is sent only to openrouter.ai. It never goes into the page, a URL or the console. The default model is Claude Opus 5.5, and DeepSeek V4.1 Flash is offered as the fast option, routed to the fastest provider. You can also give a custom model id. Each round sends the module with its locked ranges, the failing cups with a snapshot of the lane, the line errors and a digest of the rule cards. The model answers with line edits. A live transcript is recorded in the same format as the scripted ones, so any live session can be replayed later.

7 · What the checker hands the editor

For each function the kernel returns a list of cups, line errors and lane chips, and the editor draws only from that list (research 16 §4.3). Each cup records its line, the operand it sits beside, its kind, its goal as text, its verdict, what fed it, which assumptions it rests on, which runtime checks it depends on, and a witness if it was refuted. 8 · Rules we kept, and what is actually proven

Darkred means violated

Darkred is used only for a refuted cup, a failed check or a failed prove. An unfed cup in gradual mode is gray, because a missing proof is not a bug.

Held on this run is not proven

A runtime-checked cup that passed on your run is still gray. Anything that rests on one carries a *. Nothing downstream of a check is ever drawn as plain proven.

Blame goes where the fix goes

A missing proof, a wrong proof, a code bug and a spec bug each look different (§3, §4). The commentary sits on the line you would change.

One margin, Codillon’s idiom

Proof cups sit in the instruction’s own fraction, wires sit beside the value ribbons, and errors appear as far-right commentary. There is no side window you have to open to learn whether a line is safe.

Erasure line for line

Proof lines become nop and refinements are erased from the binary, so the line count is unchanged. The program you run is the program you proved, with exactly the same steps.

Explicit, not searched

Every feed is a wire to a line you wrote. The kernel looks facts up and checks prove steps, but it never searches for a proof.

An instructor axiom is a lemma with an empty body, exported as axiom:…. It is trusted, shown hatched and labelled assumed, and listed on the header badge (VERIFIED · 1 axiom on the gcd harness). Only the student’s side may declare one. Primality is in the editor ↗, but it needs three measures, an induction lemma and three axioms, so it is capstone material, not intro material.

Limits

  • Partial correctness. A fully proven function never traps on an input that meets its entry contract, and it returns results that satisfy its result type. But ordinary loops and recursion are not proven to terminate, and call-stack exhaustion is excluded. Predicates, measures and lemmas must be total. Version 1 at least had (@decreases …).
  • No memory frame rules. After a store, facts about memory-reading predicates are gone. Preserving a memory invariant across a store is runtime-checked or needs an instructor axiom (7 cups in the hash table).
  • Nonlinear arithmetic stops at monomial atoms plus interval substitution. Anything more needs a lemma.
  • prove k is positional. It takes the k most recent lane facts. Inserting an unrelated call or br_if between a fact and its prove silently changes which facts it takes (the wrong-cup isqrt is a two-line swap). An older fact must be re-cited through a fact local. Explicit references (prove @14 @22) remain an open question.
  • Outside v2: floats are opaque. call_indirect, tables, reference types, SIMD, multiple memories and memory.grow are not covered. There is no congruence for opaque terms (the gcd harness routes around it by naming values in locals), and no ghost integers, so harnesses compute in i64.
  • Proof lines to write. The intro functions need four to six prove lines each. Version 1’s Z3 found that arithmetic on its own.
  • Instructor axioms are trusted. The design allows an axiom to be justified outside Codillon, for example in Lean, but that bridge is not specified yet (open question 6).
