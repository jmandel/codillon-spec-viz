8 · What the checker hands the editor

For each function the kernel returns a list of cups, line errors and lane chips, and the editor draws only from that list (research 16 §4.3). Each cup records its line, the operand it sits beside, its kind, its goal as text, its verdict, what fed it, which assumptions it rests on, which runtime checks it depends on, and a witness if it was refuted. Here are two cups from the wrong-override isqrt variant, as recorded in the test oracle (research/v2-examples/isqrt-wrong-cup.expect.json, abridged, with that file’s raw line numbers). A feed is lookup (the matched fact), eval, auto (the facts the automatic proof used, top of lane first, after every fact it did not need was dropped), prove (an override line and the facts it took), dead, or none. The editor draws one wire per listed fact, so a proof the kernel found looks exactly like one you wrote. The oracle for the 15 examples is 214 cups. It was first derived by hand from the rule cards (research 17). After automatic proofs it was re-derived: formerly prove-fed cups take their feed from the kernel, and every verdict in the unchanged examples had to stay the same, cup for cup (research 24 §7). The decision procedure was fuzzed against exhaustive 8-bit evaluation and gave 0 unsound answers in 700 cases.

9 · Rules we kept, and what is actually proven

Darkred means violated

Darkred is used only for a refuted cup, a failed check or a failed prove. An unfed cup in gradual mode is gray, because a missing proof is not a bug.

Held on this run is not proven

A runtime-checked cup that passed on your run is still gray. Anything that rests on one carries a *. Nothing downstream of a check is ever drawn as plain proven.

Blame goes where the fix goes

A missing proof, a wrong proof, a code bug and a spec bug each look different (§4, §5). The commentary sits on the line you would change.

One margin, Codillon’s idiom

Proof cups sit in the instruction’s own fraction, wires sit beside the value ribbons, and errors appear as far-right commentary. There is no side window you have to open to learn whether a line is safe.

Erasure line for line

Proof lines become nop and refinements are erased from the binary, so the line count is unchanged. The program you run is the program you proved, with exactly the same steps.

Found, then shown

The kernel finds which facts imply a cup, with one bounded procedure run in a fixed order, so the same text gets the same proof everywhere. Then it draws what it found: the proposition on the line, a wire from each fact used, and an account one keystroke away. Automation removes the typing of proofs, not their visibility.

An instructor axiom is a lemma with an empty body, exported as axiom:…. It is trusted, shown hatched and labelled assumed, and listed on the header badge (VERIFIED · 1 axiom on the gcd harness). Only the student’s side may declare one. Primality is in the editor ↗, but it needs three measures, an induction lemma and three axioms, so it is capstone material, not intro material.

Limits

  • Partial correctness. A fully proven function never traps on an input that meets its entry contract, and it returns results that satisfy its result type. But ordinary loops and recursion are not proven to terminate, and call-stack exhaustion is excluded. Predicates, measures and lemmas must be total. Version 1 at least had (@decreases …).
  • No memory frame rules. After a store, facts about memory-reading predicates are gone. Preserving a memory invariant across a store is runtime-checked or needs an instructor axiom (7 cups in the hash table).
  • Nonlinear arithmetic stops at monomial atoms plus interval substitution. Anything more needs a lemma.
  • The override is positional. prove k takes the k most recent lane facts, so inserting an unrelated call or br_if between a fact and its prove changes which facts it takes. It is now needed only for speed or steering. Explicit references (prove @14 @22) remain an open question.
  • Search has a cost. Most functions check in well under a millisecond. Primality’s costly arm takes about 20 ms without its override, and each function has a budget of 16,384 automatic proof cases (research 24 §5, §7).
  • Outside v2: floats are opaque. call_indirect, tables, reference types, SIMD, multiple memories and memory.grow are not covered. There is no congruence for opaque terms (the gcd harness routes around it by naming values in locals), and no ghost integers, so harnesses compute in i64.
  • Facts to write. The kernel does the arithmetic, not the insight. Loop invariants, refined locals, unfold steps, and lemmas for nonlinear steps are still written by hand. Its accounts are case analyses on the goal failing, not yet the forward chain a person would write.
  • Instructor axioms are trusted. The design allows an axiom to be justified outside Codillon, for example in Lean, but that bridge is not specified yet (open question 6).
