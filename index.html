Codillon with refinement types

A visualization study: when types carry predicates, how should the editor draw whether a program meets its specification?

Codillon is Keith Winstein's structured WebAssembly editor for Stanford's intro course. Today it shows validity continuously and spatially: types are shapes, dataflow is curves, badness is dark red, and runtime is a slider. This study asks what a next version would look like if types were refinement types grounded Lean‑style ((i32 | even v), loop invariants, function contracts, a hash table's representation invariant) and the editor had to make a specification‑adherence bug as visually obvious as a type error is today.

v2 · current
From annotations to proofs as values: why version 1 was replaced

Version 2 drops the separate annotation language and the solver. Proofs are Wasm values in a fact lane: a comparison followed by if or br_if gives each arm a fact, every proposition an instruction needs is a cup, and a cup with nothing to feed it is empty. Refined block and function types are the only spec syntax (a loop's block type is its invariant), unreachable consumes a proof of False (so a harness ending in unreachable is a functional spec), and the kernel finds the arithmetic between facts itself with a small deterministic decision procedure, drawing every fact it used (an optional prove k can name the facts instead). A kernel checks the text with no Z3 and no “unknown”: every cup is proven, refuted, runtime‑checked or assumed. A vericoding mode lets an LLM write bodies and proofs against a spec the student owns.

Version 1 (first iteration): findings

The ten are not alternatives; they sort into three layers. Always-on in the margin: the sequent fraction (03) carrying value‑space regions inside the shapes (01), with a spill glyph for a failed fit and an empty cup for a missing fact. On failure: a synthetic proof hole inserted after the offending line (10) and the counterexample replayed onto the slider as a witness pill (07). On selection: lenses for integers (02), time (09), loops (05), memory (06) and coverage (08). Six epistemic states, all readable in grayscale, are shared by every prototype; the critical one is keeping “held on this run” from ever looking like “proven”.
